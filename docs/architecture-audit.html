Architecture audit — src/nemar/

2026-05-28 · main @ f722dbc · run via /improve-codebase-architecture

Four deepening opportunities in src/nemar/. Each one passes the deletion test — removing the module concentrates complexity, or in these cases, removes complexity that was never earning its keep. Two further candidates were considered and ruled out as marginal keepers. Interface designs are deliberately not yet proposed; pick one and I'll grill the shape with you.

Candidates (ranked by friction-per-LOC)

① BidsQuery + BidsPath are knit at a distance

Files
src/nemar/_bids.py:19–78 (BidsPath), src/nemar/_bids.py:82–147 (BidsQuery.from_filters), plus the matching predicate that actually fires in src/nemar/_selection.py.
Symptom
Two value types live in one module; the matching that joins them lives in another. Reading "what did my BIDS filter just do?" forces a bounce across three files (_bids.py for the path parse, _bids.py again for the filter shape, _selection.py for BidsPath.matches()). The interface promises a semantic BIDS query; the actual semantics live in the consumer.
Deletion test
Fold the matching predicate into _selection.py — no complexity concentrates anywhere new, the matching logic lands one read away from the plan builder that calls it. Keep the dumb value types (BidsPath, BidsQuery) close to their data.
Direction
Hoist BidsPath + BidsQuery to _models.py (dumb value types live with other dumb value types); move matches() and .from_filters() normalization into _selection.py so semantics live with the consumer. Fold

② SelectionPlan as a class masks the flow it implements

Files
src/nemar/_selection.py:45–268
Symptom
Three operations on one object, but they are not a cohesive composition: .build() (classmethod, three hidden phases), .raise_if_unmatched_includes() (validation), .final (the result). The orchestrator calls all three in sequence (_download.py:298–305). The class is a carrier for "selection result plus diagnostic metadata," dressed as an entity with behaviour. The interface masks the flow.
Deletion test
Promote .build() to a module-level select_files(...) that returns (selected, unmatched_includes). The orchestrator reads top-to-bottom; the diagnostic carrier disappears into a tuple. No complexity concentrates — the three steps were already linear.
Direction
Replace the class with a module-level function; or reduce it to a pure @dataclass(frozen=True) result type with no methods at all. Fold

③ LocalDataset is a two-method class with one caller

Files
src/nemar/_download.py:60–120
Symptom
A two-method dataclass (.from_dir(), .assert_compatible_with()) that was folded into _download.py in a previous simplification round. Its docstring concedes it is inlined here because _run is its only caller. Two public methods, one consumer — the canonical shallow shape.
Deletion test
Inlining both methods into _run after the manifest fetch costs ~35 LOC of orchestrator and kills one level of indirection in the critical path. The compatibility check is one of the six orchestration steps; it does not deserve its own type.
Direction
Inline into _run as a small block (or a module-private function); drop the class. Fold

④ Error re-export split: errors.py ↔ _errors.py

Files
src/nemar/errors.py (36 lines of re-exports), src/nemar/_errors.py (128 lines of definitions).
Symptom
Every exception is defined in _errors.py and re-exported in errors.py. The split was meant to keep "internals private," but exceptions are fundamentally user-facing (callers catch them by class). There is no internal-only exception in the tree. Internal code uses from nemar._errors import …; user code uses from nemar.errors import … — two namespaces for one domain.
Deletion test
Rename _errors.py → errors.py; delete the re-export file; update internal imports. No complexity concentrates; pure ceremony evaporates.
Direction
Single public errors.py; one import path; one home. Fold
